# Automation design

The recommended ten connector stages are retained; setup_vault.sh phase numbers are not lab IDs. `labs/manifest.yml` (JSON-compatible YAML) is the executable lab registry. The graph is cumulative for structure; only selected features are configured. Preparation converges the previous completed lab on a clean instance and subsequently preserves learner work. Lab 01 is a source-inspection baseline.

## Source observations

- The original seeder truncates six tables on every run and assumes roles exist before creating RLS policies. Its default fixture directory differs from tracked `data/output`; automation seeds from tracked `data/fixtures`. New setup seeds a fresh schema transactionally once; it never truncates populated tables.
- The original AppRole example already issued dynamic credentials, contrary to the recommended static AppRole stage. It now reads KV, leaving dynamic issuance to the next lab.
- The original Agent connector duplicates direct Vault API access. The migration supplies a file reader and tests it independently.
- JWT examples use a backend identity password grant, then apply caller role mapping inside the application. They do not exchange each caller JWT with Vault. This remains a documented application trust boundary; this migration does not claim end-to-end caller-bound Vault identity.
- Original fixed names, public ports, local environment, raft storage and optional service dependencies make testing in the original project unsafe. Automation creates a distinct Compose project, private generated configuration and learner workspace. It does not modify the old `.env` or `backend/connector.js`.
- Active Vault config is `vault/config.hcl`, with raft at `/vault/file` and `vault_v2.hclic`. Other Vault config files are not the deployed configuration.

## Ownership

| Resource/API path | Owner | Scope |
| --- | --- | --- |
| automation Compose services/networks/volumes | Compose, lifecycle Ansible | Dedicated project; original Compose remains supported |
| sys/init, sys/unseal | Ansible bootstrap | Read live state; preserve recovery JSON privately |
| sys/policies/acl/zt-bootstrap-* | Ansible bootstrap | Only automation identities, distinct names |
| sys/mounts/secret, sys/mounts/database | Terraform | Mount structure only; prevent_destroy |
| sys/auth/approle, sys/auth/jwt | Terraform | Auth mount structure only; prevent_destroy |
| sys/policies/acl/app-policy, zero-trust-jwt-lab, zt-static | Terraform | Application policy content |
| secret/data/postgres | Ansible | Secret value; CAS-aware comparison |
| database/config/postgres and database/roles/* | Ansible | Operational config and SQL; credentials never Terraform |
| auth/approle/role/zero-trust-app and issued secret IDs | Ansible | Role settings, private runtime delivery |
| auth/jwt/config and auth/jwt/role/zero-trust-jwt-lab | Ansible | Backend identity issuer/audience binding |
| PostgreSQL schema, seed, groups, grants and RLS | Ansible | Transactional initial migration; scoped role stage |
| LDAP entries; Keycloak realm, federation, groups, roles, clients | Ansible | Compare before writes; preserve passwords |
| learner connector and backend runtime environment | Ansible | Local source, protected edits, conditional recreation |
| Agent rendered credentials/leases | Vault Agent/Vault | Runtime writers; automation does not overwrite output |

Bootstrap order: preflight → private workspace → Compose prerequisites → DB/LDAP/Keycloak → Vault live bootstrap → scoped Terraform token → structure apply → non-secret output contract → scoped Ansible configuration → runtime identity delivery → connector deployment → live verification.

One Terraform root uses a protected local backend path per instance. License delivery follows vault_reference: config/defaults.env, then .env, then direct VAULT_LICENSE container environment. No license file is generated by automation.

Provider authentication is inherited only from a private token file via environment; provider child tokens retain bounded lifetime. Terraform structure is cumulative; a lower desired level cannot remove higher resources. Before apply, detect existing unmanaged resource IDs and require explicit import. Verification never imports or applies.

## Runtime and portability

Docker uses the installed Compose plugin or docker-compose v2. Podman uses its external Compose provider. The adapter probes both engine and provider and records the resolved endpoint identity. An explicit engine always wins; ambiguous auto selection fails with instructions. Mutation locks include engine target and project; nested calls remain inside the dispatcher lock. VM bind-mount behavior requires live validation, not a static parity claim.

Automation builds backend/frontend from pinned existing Dockerfiles, runs node directly for predictable restarts, and binds generated source. Ports use a configurable base distinct from the legacy stack. It preserves frontend/backend/data separation; the backend and data networks are internal, with published controller ports bound only to loopback. Ollama, Boundary, OS rotation and MinIO remain in the legacy optional path.

The design reuses shift_gear ownership boundaries, scoped bootstrap, ordered phases, private state, non-secret handoffs and independent live checks. It excludes CRC, OpenShift, namespaces, Kubernetes controllers, the seal chain and dashboard.
